# Testing — the test JSON, when tests run, what they check

Every protocol must be **covered by a test** — but you only hand-write tests for *some* of them.
The engine **auto-tests** every protocol it can run with **no arguments**, and asks you for an
**explicit test** only where it can't (a protocol with a mandatory argument). Either way a test
today answers one question: **does the protocol run without failing?**

Understand what tests do and don't verify: they confirm the app **runs end to end and produces
output** — the plumbing — **not** that the output is numerically correct. A green test means "the
protocol compiled, its data-model references resolved, and it executed without crashing," not
"the numbers are right." **A protocol that runs but computes the wrong numbers passes CI
indistinguishably from a correct one** — so a green suite is not scientific validation. There are
**no result-level assertions today** (a wanted future addition, complicated by source data that
legitimately changes between runs); the current correctness check is **manual — open the written
`_test_results/` output and eyeball it.** For a clinical platform, treat that as a required step,
not an afterthought.

## The test JSON

One file per test under `tests/`, registered in `main.json`'s `tests` array. Shape:

```jsonc
{
  "protocol_instance": {
    "name": "python_bp",              // a registered protocol's unique id (from main.json)
    "arguments": {                    // values for the protocol's arguments (see below)
      "background_cohort": { "data_function_type": "categorical-all" }
    }
  },
  "output": "_test_results/test_python_bp.html"   // where the run writes its result
}
```

- **`name`** references a protocol by its **registered id** — the `protocol_definition.name`. This
  resolves for **any** registered protocol, whether it's a top-level app in `main.json` *or* a
  **helper** discovered by file-path reference (`protocols.md`). So you **can** write a targeted test
  for a helper like the cohort builder: reference it by its name (`"cohort"`) even though its file
  isn't in `main.json`'s `protocols[]` — put the test in `main.json`'s `tests[]` as usual. (Helpers
  with no mandatory arguments are auto-tested anyway; an explicit test lets you drive a specific
  case, e.g. a cohort subset.)
- **`arguments`** is a map of argument key → value. **Every mandatory (and minimum-one)
  argument_set must be satisfied**, or the protocol errors. Three value shapes:
  - a **data_function**, e.g. a cohort: `{ "data_function_type": "categorical-all" }` (all
    entities) or `{ "data_function_type": "categorical", "collection": "Department", "variable":
    "Cardiology" }`;
  - an **array of level names** for a checkbox/selection argument, e.g. `["Sepal width"]`;
  - a **raw scalar** — the argument's plain value: a **string** for a filter pick
    (`"cohort_clinic__Department": "Cardiology"`) or a **boolean** for a toggle
    (`"include_all_dna_variants": true`, as `test_download_all_genotypes.json` does).

  **Argument key format.** An autogenerated (expander) argument is keyed
  **`<argument_set_name>__<column>`** — the argument_set name, a **double underscore**, then the
  collection/variable display name. So to test a specific **cohort subset**, target the filter
  directly: `{ "cohort_clinic__Department": "Cardiology" }` runs the cohort builder with only
  Cardiology selected (the clinic's builder returns 3 entities for that). Use this for targeted
  regression tests; use `categorical-all` when you just need to satisfy the cohort to let a protocol
  run.
- **`output`** is the file the run writes; its extension matches the protocol's `output_type`
  (`.html`, `.csv`, `.parquet`, `.png`). `_test_results/` is gitignored.

The clinic example ships one test per protocol (`tests/test_*.json`) — copy their shape.

## Auto-tests vs explicit tests

This is the split that decides which protocols you must hand-write tests for.

- **Auto-tests** run **every protocol that has zero mandatory arguments** — automatically, no
  file needed. That set is larger than it looks: it includes the many **`argument_protocol`s**
  autogenerated from the protocol/argument tree (the ones that fetch a control's options). Each is
  simply executed with no arguments. Because running one requires its **collections — and any
  named variables — to actually exist in the built archive**, the auto-test suite is a broad,
  free **data-model integrity check**: rename or drop a collection a protocol references and its
  auto-test fails.
- **Explicit tests** are the `tests/*.json` files you write, needed for any protocol that has **at
  least one mandatory argument** — the engine can't invent a valid value, so it registers that
  protocol as **missing a test** until you supply one with **toy arguments that satisfy the
  mandatory contract** (a cohort satisfied with `categorical-all`, a checkbox with one level).

So **coverage = every protocol either auto-testable (no mandatory args) or given an explicit
test.** A protocol with a mandatory argument and no explicit test is the coverage gap `compile`
reports.

> **Developer rule — when you author a new protocol, wire it into `main.json` completely:** register it
> in **`protocols`**, place it in **exactly one `categories` collection** and its appropriate
> **`tags`** (collections = app type, tags = data type — see `manifest.md`), **and** write its
> **`tests/*.json`** *unless* it has **no arguments at all** or **only optional argument_sets** (those
> auto-test). Everything else needs an explicit test, and
> **`compile`'s test-coverage warning is your indicator** — `Insufficient test coverage … No test for
> registered protocol 'X'` means write one. **`minimum-group` argument_sets count as non-optional as a
> group:** the engine requires **at least one** argument selected *across all* the group's sets to run,
> so the test must supply at least one (e.g. one analysis variable via
> `<argument_set_name>__<collection>: <value>`) or it fails with *"Minimum group across argument sets is
> missing an argument selection."*

## When and how tests run

- **Coverage** is checked at **`compile`** (fast, no data — `dev-loop.md`).
- **Execution** must be **turned on** — it is *not* automatic just because `tests` is set. Set
  **`run_tests: "true"`** in the manifest's **`serve`** block (the example's manifests do), or pass
  **`run_tests=true`** on the CLI. On `run_server` the tests then run **on startup, asynchronously**
  — the server keeps serving while they execute, so **wait for them** (watch for the result files /
  the log). For a one-shot CI run, add **`die=true`** to run everything and exit:

  ```bash
  java -Xmx4g -jar ${TAGBIO_JARS}/fc_csv_server.jar run_server manifest=manifest.json \
      r_sdk=${TAGBIO_R_UTILS} python_sdk=${TAGBIO_PY} run_tests=true die=true
  ```

- Plugin tests need the **R/Python SDKs** on `r_sdk` / `python_sdk`, the SDK's **console scripts on
  `PATH`** (e.g. `connect_tagbio_py`), and every library the plugin imports installed in the
  environment / container (`governance.md` → `build-container.sh`), or the test fails at load.

## What pass and fail look like

A test today checks only **that the protocol does not fail**:

- **Fail → the whole server process goes down.** There is no soft failure. Be precise about the
  sequence: the server **starts and begins serving**, the tests run **asynchronously**, and if any
  test fails the **entire process exits** (non-zero) — a **delayed kill**, not a pre-serve gate.
  So a deployment with a failing test **won't stay up**: it comes up, self-terminates seconds
  later, and won't keep serving a broken build (there is a brief serving window before it dies —
  it's not a hard "refuse to start"). With `run_tests: "true"` in the `serve` block, that makes a
  **production** deployment self-validate its own archive on startup and fail loudly — catching an
  **incompatible deployed archive** (one that differs from what you built and tested locally) or a
  **failure that wasn't tested properly and got pushed to production**. For a **build/CI** gate, use
  `die=true` to run the tests once and exit non-zero on failure. Typical causes of a failure: a
  data_function naming a collection/variable that isn't in the archive, a missing plugin library, an
  unsatisfied mandatory argument, or an output-path/`output_type` mismatch. Read the log (raise
  `verbosity`) and cross-check `data-functions.md` / `troubleshooting.md`.
- **Pass → the result file is written** to the test's `output` path (locally, **gitignored**) for
  you to open and eyeball. Nothing about the *contents* is asserted — inspection is manual.

## Recipe: add a test for a protocol

1. Create `tests/test_<name>.json` with `protocol_instance.name` = the protocol's id.
2. Supply values for **every mandatory argument** (satisfy a cohort with `categorical-all` if you
   just need it to run).
3. Point `output` at `_test_results/…` with the right extension for the `output_type`.
4. Register it in `main.json`'s `tests` array.
5. `compile` (coverage passes) → `run_tests=true` (it executes).
