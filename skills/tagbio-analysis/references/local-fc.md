# Serving a product locally and querying it

The Tag.bio notebook ships **Java 21 and the FC engine jars** (`/tagbio-jars`, `TAGBIO_JARS`), so
you can build and serve a product locally and point the SDKs at it. This is the fastest way to work
without touching a deployed product at all.

**When this is the right tool:** developing or debugging analysis code against a small or synthetic
product; reproducing a colleague's build; checking whether a collection you need actually exists
before requesting access to production. **When it isn't:** production analysis — use the deployed
product.

## The three commands

Run from an FC repo's root (paths in the manifest are relative to it):

```bash
# 1. compile — validate config + protocols WITHOUT loading data (seconds)
java -Xmx4g -jar $TAGBIO_JARS/fc_csv_server.jar compile manifest=manifest.json

# 2. build_archive — read the sources, apply the model, write the immutable archive
java -Xmx4g -jar $TAGBIO_JARS/fc_csv_server.jar build_archive manifest=manifest.json verbosity=4

# 3. run_server — load the archive and serve the API + UI on localhost:8000
java -Xmx4g -jar $TAGBIO_JARS/fc_csv_server.jar run_server manifest=manifest.json \
     r_sdk=$TAGBIO_R_UTILS python_sdk=$TAGBIO_PY
```

Most repos wrap these in `_shell_scripts/{compile_local,build_archive,run_server}.sh` — prefer the
repo's own scripts, which carry its correct jar and heap settings.

**Pick the jar for the source:** `fc_csv_server.jar` for local CSV/TSV; `fc_sql_server.jar` for a
SQL-sourced build (it also handles CSV, so it's the superset); the cloud jars
(`fc_s3_server` / `fc_gcp_server` / `fc_azure_server`) serve an archive from object storage. Raise
`-Xmx` for a big product — a real one may need 16–32g.

## What to check after a build

The build writes a **`data_dictionary.tsv`** listing every collection and variable it produced —
the ground truth of what exists. If a collection isn't there, it wasn't built, and no amount of
querying will find it. Also read the log for:

- **per-table row counts** — a table that loaded 0 rows means a bad path, delimiter, or filter;
- **"N entities loaded into data model"** — wrong number means a non-unique key merged rows;
- **"Post-processing of N parsers complete"** — fewer than expected means a parser was skipped.

Treat `data_dictionary.tsv` and the build log as **sensitive** for a real product: the log can
contain raw source values from a failing parser. Don't paste their contents.

## Startup order matters when you query it

`run_server` starts up in this order: **load the archive → run the auto-tests → begin serving
queries.** The query API is live only at the third step. On a large product with many autogenerated
tests that window can run to **minutes**, so a query fired the instant the process starts simply
won't connect. Wait for the serving line in the log.

Also note: **a failing test takes the whole server process down** — a delayed kill, not a soft
failure. If your local server dies seconds after coming up, read the test output, don't blame the
port.

## Connect to it

No authentication — it's localhost.

```r
con <- tagConnect(host_url = "http://localhost:8000")
fc  <- tbl(con)                     # NO product name on localhost (R errors if given one)
df  <- fc %>% select(`Department`) %>% collect()
```

```python
fc = tagbiopy.fc.FC(fc_name="fc-<name>", host="http://localhost:8000")   # name optional here
df = fc.df.select("Department").run()
```

Two localhost quirks: **`colnames(fc)`/`summary` come back empty** on a localhost serve, so select
by literal name or enumerate from `data_dictionary.tsv` / the config; and on **older tagbiopy
(< 1.0.1)** only port **8000** works — other ports get force-rewritten to `https` and demand a key.

## Serving more than one at once

R can talk to any port, so you can serve two products side by side:

```bash
java -Xmx4g -jar $TAGBIO_JARS/fc_csv_server.jar run_server manifest=manifest.json port=7999
```

```r
con2 <- tagConnect(host_url = "http://localhost:7999")   # no auth
```

Useful for developing a cross-product join locally. Keep the second port ≠ 8000 so it doesn't
collide with a build's own transformer-callback server.

## Guardrails still apply

`run_server` is **unauthenticated**. Never bind it beyond localhost, and never serve real or
regulated data from it as if it were production. Building from real sources is a **data access** —
get consent first, exactly as for a deployed pull.

For anything beyond running these commands — changing the config, adding a protocol, writing a
plugin or transformer — use the **`fc-authoring`** skill.
