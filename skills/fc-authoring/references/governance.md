# Governance — identity, deployment, and access control

This platform is built for **regulated biomedical data**, so who can reach a product and who can
see which parts of it are first-class concerns.

**The key mental model: an FC does not own user identity or authentication — the greater system
does.** An FC is designed to **run anywhere**, and it trusts the surrounding system to establish
*who the user is* and *which groups they belong to*. The FC's job is to **enforce access against
the identity it is handed** on each request, not to log anyone in. (It is a *pure core* with the
messy concerns — identity, authentication — kept at the edge, in the system around it. This is why
the same FC binary runs both on a laptop and inside a governed cluster.)

## Local (`run_server`) is a dev/testing harness, not production

The local `run_server` (`dev-loop.md`) serves the API and UI on `localhost:8000` with **no auth**.
It is a **development and testing** system — fine for synthetic or non-sensitive data — **not** a
production deployment.

> **Guardrail:** never treat localhost as production, and never bind it beyond localhost with real
> or regulated (PHI-shaped) data. Development against sensitive data still requires the user's
> informed consent (`SKILL.md` → Guardrails).

## Production: identity is established outside the FC

In the Tag.bio cluster the identity plumbing lives **above** the data products:

- Users authenticate through **standard enterprise single sign-on** — e.g. OAuth/OIDC, or **SAML**
  federated to an organization's own **Identity Provider (IdP)** — and the cluster manages the
  **user/group → FC authorization** (who may reach which product). The exact method varies by
  deployment; the FC doesn't care which, because identity is settled *before* the request reaches
  it.
- A **gateway** sits in front of the FCs. It performs its own authn/authz check on each request
  and passes the caller's **groups and auth token** through to the FC's API.
- The FC therefore receives an already-authenticated identity plus its groups **per request**, and
  applies the access-control layers below to *that* — the same FC binary runs unauthenticated on a
  laptop and fully governed in the cluster, because it never owned the login in the first place.

## Enforcement knob: the `groups` flag

The `groups` flag is **not the FC's front door.** Whether a given user can reach a product at all is
decided **upstream** — by SSO and the cluster's back-end-for-frontend/gateway (above). The `groups`
flag only tunes what the FC does **with the groups it's handed**, and in practice its main use is
**masking protocols** (e.g. hiding developer-only protocols from end users), not gating data
access. So `groups=false` is **not** "security off" — access is still governed upstream; it just
means the FC itself does no additional group filtering.

| `groups=` | Behavior |
|---|---|
| `false` | the FC does no group filtering of its own (access is still enforced upstream) |
| `lax` (default) | enforce the groups a protocol declares, but still allow `callback_script`s |
| `true` | require the `developer` group to run scripts and **disallow** `callback_script` from arguments (most restrictive) |

A **`callback_script`** is a script an **argument** can carry that the server runs to compute its
options — i.e. **arbitrary code supplied through the request**. That is the security concern:
`groups=true` forbids it (and requires the `developer` group to run any script) so that serving
sensitive data can't execute caller-supplied code. Use `true` in that setting.

**This does not block your filters.** An **`argument_protocol`** (the helper that populates a
cohort filter's options, `arguments.md`) is **FC-authored** — a declarative protocol in your repo,
usually autogenerated by `argument_expanders` — not code supplied through the request. It runs like
any protocol, subject to the normal protocol `groups`. So an `argument_protocol`-driven cohort
builder **keeps working under `groups=true`**; only **caller-supplied `callback_script`s** are
disallowed. The line is *authored-in-the-FC (trusted)* vs *arrives-in-the-request (untrusted)*.

## Two layers of access control

**1. Collection-level — who can see which data.** A **`groups`** attribute restricts the resulting
collections to those auth groups, and it **cascades by scope** — set it as narrowly or as broadly
as you need:

- **On a parser** → just the one collection that parser produces.
- **On a table** → every collection from that table (applied to all its parsers).
- **At the top-level config** → product-wide, the same way `null_indicators` cascades to everything.

The transformer ingestion format carries the same control as its **`auth_groups`** column
(`transformers.md`) — a blank value means "visible to all." Use this to keep sensitive collections
(identifiers, rare diagnoses) out of view for users who shouldn't see them, while the rest of the
product stays open.

**2. Protocol-level — who can run which app.** `main.json` can carry a **`groups`** map of
`group_name → [protocol files]`, restricting those protocols to members of that group:

```jsonc
{
  "groups": {
    "clinical_reviewers": ["protocols/protocol_phi_report.json"]
  }
}
```

A protocol definition may also declare **`download_groups`** — the groups allowed to convert its
result into a raw **download** (export gate), so you can let everyone see a summary but restrict
row-level export.

## How `method: external` plugin apps are governed

An ordinary R/Python **plugin protocol** is governed by exactly those two layers — `groups=true` does
**not** silently lock analysts out of it. The sequence makes it concrete:

1. **Protocol-level check first, at request time.** When the FC API receives a request to run the
   protocol, it checks the caller's groups against the protocol's `groups`. If they don't qualify the
   protocol doesn't run — and it isn't even **exposed to the client** (its existence is hidden). So a
   plugin app is gated the same as any other protocol.
2. **The plugin then runs in "override" mode.** The R/Python code runs *inside the container* and
   reaches the FC over **localhost**, so its own callback isn't re-authenticated as an outside caller
   — but the caller's **user token is still carried through**.
3. **Collection-level check on the callback.** When the plugin (via the SDK) pulls the dataframe
   defined by the protocol's `background` + `analysis_variables`, that pull is enforced against the
   caller's groups at the **collection level**. So a plugin can only ever return data the caller is
   allowed to see.

Net: plugin apps obey the same protocol-level gate (who may run/see it) and collection-level gate
(what data comes back) as everything else. `groups=true` specifically blocks **caller-supplied
`callback_script`s** (untrusted code arriving in the request) — not your FC-authored plugins.

## Plugin libraries: `deploy/build-container.sh`

A deployed FC runs in a **container image**. The base image ships the tidyverse (ggplot2, dplyr,
tidyr, …) and the Tag.bio SDKs (`tagbio` for R, `tagbiopy` for Python), but **any other library a
plugin imports must be installed into the image** — via the FC's own **`deploy/build-container.sh`**
(each FC has its own). Miss one and the build/serve fails at load with `no package called '<X>'`.

The example ships `deploy/build-container.sh`. Its contents mirror exactly what the toy's plugins
need beyond the base: **R** `r-plotly` (the R plugin), and **Python** `plotly`, `papermill`,
`nbconvert` (the Python plugin and the notebook plugin). The rule: **for every `library()` /
`import` a plugin makes, confirm the package is in the base image or add it here.** (Locally, an R
plugin can `if (!require(x)) install.packages(x)` as a convenience, but the container is the real
answer — bake it in.)

## From localhost to the cluster

A deployed product is served by a **cloud jar** (`fc_s3_server` / `fc_gcp_server` /
`fc_azure_server`, `configuration-and-sources.md`) reading the archive from object storage — or, as
in the example's `deploy/deployments.yml`, built in-cluster from the config with the CSV/SQL jar. A
deployment is described by **`deploy/deployments.yml`**, one top-level key per deployed instance
(the example ships one; see `manifest.md` → "One repo, many instances"). Each entry carries:

- the source (an **archive** path + storage coordinates like `s3_bucket` / `aws_region`, **or** a
  `config` to build in-cluster) and the **`main`** file + R/Python SDK paths;
- the **jar** (e.g. `fc_s3_server.jar` for a bucket archive, `fc_csv_server.jar` to build from CSV)
  and JVM sizing (`Xmx`, `Xss`) — **tune `Xmx` to the data**, enough to run analyses, not more than
  the node has;
- **secrets by reference** (e.g. a `secretRef` to cloud credentials) — credentials live **outside
  the repo**, never in it;
- health/liveness (`livenessProbe`) and resource `reservation`s for the orchestrator.

One FC often runs **multiple instances** — each its own key here; the shared `main` must resolve
for every instance.

### HTTPS and API keys

For a reachable endpoint, serve over TLS with `https_key_store` + `https_password_file`, and issue
programmatic access with `api_key_count` to mint API keys. These are set on the server invocation,
not in the config. In the **managed cluster** the gateway in front of the FC typically terminates
TLS and handles auth (above), so these FC-level flags matter mainly for **standalone / self-managed**
serving outside that gateway.

## Versioning and reproducible deploys

The archive is **immutable** (`manifest.md`): a rebuild produces a new archive rather than mutating
one in place, which is what makes a served product a fixed, citable dataset. For a **reproducible**
build/serve, pass **`commit=<repo commit>`** in production: it **pins the FC's repository — config,
parsers, protocols, main — to a specific git commit (SHA)**, so the build (and the served product)
is tied to one known, immutable source revision rather than "whatever the branch is right now." It
pins the **code/definition** side; the **data** side is pinned by the immutable archive. Together
they make a deployment fully reproducible: same commit + same archive = same product. Keep distinct
versions as distinct archives (and distinct `deployments.yml` instances); don't overwrite an archive
that something is already citing.

## Recipe: prepare an FC for deployment

1. Decide **collection** visibility: add `groups` to any table producing sensitive collections.
2. Decide **protocol** visibility: add a `groups` map (and `download_groups`) in `main.json`.
3. Choose the enforcement mode (`groups=true` for script-restricted serving).
4. Build the archive; place it in the bucket; add/point a `deploy/deployments.yml` instance at it
   with the right cloud jar, `Xmx`, and secret references.
5. Serve over HTTPS; pin the build with `commit` for reproducibility.
