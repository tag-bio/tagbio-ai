# The cohort builder and the argument layer

The **cohort builder** is how a user interactively defines a **subset of entities** — a
**cohort** — that a protocol then runs against. It is the single most important piece of the
interactive layer: nearly every FC exposes it, and most protocols run against a user-chosen cohort
rather than all entities. **Building your own is a core skill** — the generic default is only a
quick-start crutch.

It builds directly on two earlier ideas:
- **Entities and the set/tag model** (`data-model.md`): a cohort is assembled by **intersecting and
  unioning the categorical tag-sets** and numeric ranges of the data model. Because categorical
  variables are already sets of entities, "encounters in Cardiology **and** Systolic > 140" is fast
  set algebra.
- **`background`** (`protocols.md`): a protocol's `script.background` names *which* entities the
  analysis uses. Point it at a cohort and the protocol runs on the user's subset.

## Arguments and argument_sets

The interactive parameters a protocol exposes are **arguments**, grouped into **argument_sets**.
An argument_set has a **type** (`mandatory` — fill all; `minimum-one` — choose at least one;
`optional`). There are two ways to populate one, and you should **strongly prefer the first**:

- **`argument_expanders` (autogeneration — prefer this).** Point it at **data_functions** and the
  platform generates the argument controls for you: a **categorical** collection becomes a checkbox
  filter, a **numeric** variable becomes a range filter. You curate *which* collections become
  filters by listing their data_functions — no hand-written argument objects. This is the modern,
  low-maintenance path and leans on the set/tag model.
- **`arguments` (hand-crafted).** Declare each argument object explicitly. Only reach for this when
  an expander can't express what you need; it is far more verbose. (A lot of engineering went into
  the expander path — use it wherever possible.)

## Building your own cohort builder

A cohort builder is itself a **protocol** — referenced by a cohort argument's `argument_protocol` —
that **returns an entity set**. The clinic ships one; it is four small pieces.

**1. The cohort argument** the protocols expose (`argument_sets/argument_set_background_cohort.json`).
An `argument_type: "cohort"` argument, autogenerated with `argument_expanders`, pointing at *your*
builder protocol:

```jsonc
{ "argument_set_definition": { "argument_set_type": "mandatory",
                               "name": "background_cohort_argument_set",
                               "title": "Specify a Background Cohort" },
  "argument_expanders": { "argument_type": "cohort", "name": "background_cohort",
                          "title": "Background Cohort",
                          "argument_protocol": "protocols/protocol_cohort.json" } }
```

**2. The builder protocol** (`protocol_cohort.json`) — `method: "entity"` (it **returns entities**),
whose `background` **intersects** the filter criteria:

```jsonc
{ "protocol_definition": { "name": "cohort", "title": "Clinic Cohort",
                           "argument_sets": "protocols/argument_sets/argument_set_cohort.json",
                           "dependencies": "all" },
  "script": { "method": "entity",
              "background": { "data_function_type": "set-intersection",
                              "criteria": "protocols/argument_reference_sets/argument_reference_set_cohort.json" } } }
```

**`dependencies: "all"`** makes every filter **interdependent**: selecting a value re-runs the other
filters against the narrowed cohort, so their option counts update live (pick `Cardiology` and the
Diagnosis/Systolic filters now reflect just those encounters). Almost every cohort builder wants
this, so `"all"` is a shorthand for the whole dependency graph (`arguments.md`).

> `protocol_cohort.json` is **not** listed in `main.json` — a protocol referenced only by
> **file path** (here as the cohort argument's `argument_protocol`) is discovered and registered
> automatically when the compiler traverses the protocols that reference it (`protocols.md`). Only
> user-launched apps go in `main.json`.

**3. The filters** (`argument_sets/argument_set_cohort.json`) — this is the **curated** part:
`argument_expanders` lists the data_functions you want to become filters. **`method: "summary"`** is
a set-level override applied to every generated filter so each reports the counts behind its options
(`arguments.md` → set-level attributes).

```jsonc
{ "argument_set_definition": { "argument_set_type": "optional", "name": "cohort_clinic",
                               "title": "Clinic Filters" },
  "method": "summary",                            // set-level override — a sibling of the definition
  "argument_expanders": [ "protocols/data_functions/categorical_collection_department.json",
                          "protocols/data_functions/categorical_collection_diagnosis.json",
                          "protocols/data_functions/numeric_collection_blood_pressure_systolic.json" ] }
```

**4. The selection logic** (`argument_reference_sets/argument_reference_set_cohort.json`) — the
criteria the builder's `set-intersection` ANDs together, one `argument-set-reference` per filter
set:

```jsonc
[ { "data_function_type": "argument-set-reference", "argument_set": "cohort_clinic" } ]
```

**Data flow:** the user's filter picks → each filter's handler yields the matching entity set →
`set-intersection` ANDs them → the builder returns that cohort. Add more filter argument_sets (a
demographics section, a labs section) and list each as another `argument-set-reference` to AND
them. An unset filter matches everyone, so an empty cohort = all entities.

This is verified end-to-end: selecting `Department = Cardiology` returns exactly the 3 Cardiology
encounters of 8.

## `default_cohort_protocol` — the quick-start fallback (prefer your own)

**Build your own (above) for anything real.** As a stopgap only, swapping the builder's
`argument_protocol` to the reserved name **`default_cohort_protocol`** gives a working cohort builder
with zero authoring: it's **provided by the engine** (constructed from the `fc-default` base that
ships inside the platform — you do **not** clone a repo or create a
`default_cohort_protocol.json`), and it exposes **every** categorical collection as a filter. It's
fine to get moving before you've written your own, but it's undifferentiated (no curation, no
numeric filters) — the curated builder above is the pattern to learn and use.

## Wiring a protocol to the cohort

A protocol lists the cohort argument_set and points its `background` at the cohort **by value**:

```jsonc
"protocol_definition": { "…": "…",
  "argument_sets": [ "protocols/argument_sets/argument_set_background_cohort.json" ] },
"script": {
  "…": "…",
  "background": { "data_function_type": "argument-value", "argument": "background_cohort" }
}
```

**Why `argument-value` and not `argument-reference`:** a cohort's value *is already a data function*
(the FC sends the cohort definition to the client and the client sends it back), so you pass it
through **by value**. `argument-reference` would instead run the argument's **handler function** —
what the *filters inside* the builder use, not the cohort background. See
`catalog-data-function-types.md` for the full distinction. (The clinic's `protocol_download.json`,
`protocol_python_bp.json`, `protocol_rmd_bp.json`, and `protocol_ipynb_bp.json` all do exactly this.)

## More than one cohort

A protocol can declare **several cohorts** — each a separate `argument_type: "cohort"` argument
with its own `name`. A two-cohort **comparison** protocol defines `cohort_a` and `cohort_b` and the
plugin contrasts the two subsets; a protocol might also pair a `background_cohort` (the population)
with a second highlighted cohort. Give each a distinct name and reference each where needed.

## Testing a cohort protocol

A `mandatory` cohort must be satisfied in the protocol's test — use all entities:

```jsonc
"arguments": { "background_cohort": { "data_function_type": "categorical-all" } }
```

To test an actual **subset**, pass a filter selection keyed `"<argument_set>__<column>"`, e.g.
`{ "cohort_clinic__Department": "Cardiology" }`. (See `tests/test_download.json` and
`tests/test_python_bp.json` for the all-entities form.)

## Recipe: give a protocol a user-built cohort

1. Build (or reuse) a cohort builder: a `method: entity` protocol whose `background` is a
   `set-intersection` over an `argument_reference_set`, with filters declared via
   `argument_expanders` over data_functions (`protocol_cohort.json` + its argument_set).
2. Expose it through a cohort argument (`argument_type: "cohort"`, `argument_protocol` → your
   builder) — reuse `argument_set_background_cohort.json`.
3. List that argument_set in the protocol's `protocol_definition.argument_sets`.
4. Set `script.background` to `{ "data_function_type": "argument-value", "argument": "background_cohort" }`.
5. In the test, satisfy the cohort with `categorical-all`.

## Common mistakes

- **`argument-reference` for a cohort `background`.** A cohort is passed by **`argument-value`**; the
  compiler warns when an `argument-reference` targets an argument with no handler.
- **Hand-crafting filter arguments** when `argument_expanders` over data_functions would do it.
- **A cohort argument_set that isn't referenced** by any `background` — the user builds a cohort that
  does nothing.
- **Forgetting to satisfy a `mandatory` cohort in the test** — the protocol errors at test time.
- **Using `background` for columns / `analysis_variables` for the cohort** — background is the rows
  (entities), analysis_variables the columns.
