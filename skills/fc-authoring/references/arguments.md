# Arguments — the interactive parameters a protocol exposes

An **argument** is one interactive input a protocol shows the user (a cohort, a set of checkboxes,
a numeric range, a toggle). At run time each argument resolves to a **value or a data function**
that the protocol's `script` consumes — via the `argument-*` bridges (`data-functions.md`,
`catalog-data-function-types.md`). Arguments are grouped into **argument_sets**, and the
**cohort builder** (`cohort-builder.md`) is the flagship consumer. Like parsers and data_functions,
there are **many** argument types; learn the common ones here and reach for the enumeration at the
end when you need a rarer one.

## argument_sets: how arguments are grouped and filled

Every argument lives in an **argument_set**, whose **type** governs how the user must satisfy it:

| argument_set_type | The user must… |
|---|---|
| `mandatory` | provide a value for **every** argument in the set |
| `minimum-one` | choose **at least one** argument *within this set* |
| `minimum-group` | choose **at least one** across *all* sets tagged `minimum-group` (a **cross-set** requirement) |
| `optional` | may leave it empty (an empty filter matches everyone) |

> **`minimum-group` vs `minimum-one` — it's about scope.** `minimum-one` is enforced *per set*: that one
> set must have a selection. `minimum-group` is enforced *across every set that shares the type* — the
> user must make a selection in **at least one** of them, and may leave the others empty. Use it to offer
> **alternative** argument sets where filling any one is enough (e.g. a stratifier the user can pick from
> tissue **or** liquid **or** plasma, each its own `minimum-group` set). If none is filled the engine
> errors: *"Minimum group across argument sets is missing an argument selection."*

> **Wrap the identity fields.** The set's identity fields (`argument_set_type`, `name`, `title`,
> `description`, `asset`) go **wrapped** in an `argument_set_definition` object (and a hand-crafted
> argument likewise wraps its identity in an **`argument_definition`**, below). Set-level *override*
> attributes like `method` and `dependencies` are **not** identity — they stay at the top level, a
> **sibling** of `argument_set_definition`.

There are **two ways** to populate a set — **strongly prefer the first:**

- **`argument_expanders` (autogenerate — prefer).** Point it at **data_functions** and the platform
  generates the controls: a **categorical** collection → a checkbox filter; a **numeric** variable →
  a range filter. You curate *which* collections become arguments by listing their data_functions.
  No hand-written argument objects, low maintenance. (Its value may be a **list** of data_function
  paths, or a single **object** — as with the one cohort argument in `cohort-builder.md`.)

  ```jsonc
  { "argument_set_definition": { "argument_set_type": "optional", "name": "cohort_clinic",
                                 "title": "Clinic Filters" },
    "method": "summary",                          // set-level override — a sibling, not identity
    "argument_expanders": [ "protocols/data_functions/categorical_collection_department.json",
                            "protocols/data_functions/numeric_collection_blood_pressure_systolic.json" ] }
  ```

- **`arguments` (hand-crafted).** An explicit list of argument objects (below). Prefer expanders, but
  hand-crafted is **not** a legacy fallback — the clearest case it's genuinely necessary is **boolean
  logic**: a `boolean` / `boolean-null` toggle isn't generated from a collection's values, so you
  declare it. Beyond that, reach for hand-crafting only when an expander truly can't express the
  control you need. Everywhere else, expanders win.

### Overriding argument attributes at the set level

Autogenerated arguments come with defaults. To change an argument-level attribute *without* dropping
back to hand-written argument objects, **set that attribute on the argument_set** — it applies to
**every** argument the expanders generate. Most argument-level attributes have this set-level
cognate. The common ones:

- **`method`** — how each generated argument fetches its options. Three values:
  - **`"summary"`** — run each filter as a summary, so it reports the **counts/distribution** behind
    every option (what makes the live-narrowing in a cohort builder show numbers). The clinic's
    `cohort_clinic` uses this.
  - **`"variable"`** — the same option list **without** the counts (cheaper; no per-option tally).
  - **`"collection"`** — a different shape: an argument where the user **picks from the collections**
    in the referenced data_function — very commonly a **`collection_set`** — rather than picking
    values within one collection. Use it to let the user choose *which* variable/collection to
    analyze, not which values to filter on.
- **`argument_type`** — force the control type for all generated arguments (e.g. render them all as
  radios instead of checkboxes).

(The alternative — a full argument object inside `argument_expanders` with the attribute set on it —
still works, but per-set override is the light way to do it across many autogenerated arguments.)

### Interactivity between arguments: `dependencies` and `disables`

Two argument-level attributes (also settable on the set, or — for a cohort builder — on the
protocol, to apply broadly) control how selections in one argument affect others:

- **`dependencies`** — "I depend on selections in these other arguments/sets." When they change, the
  client fires a **callback** that re-runs this argument's `argument_protocol` with the current
  selection, so its options and **counts re-narrow to the live cohort**. This is what lets a user
  *see selections filter down the data* — pick `Sex = Male` and every other filter now shows the
  male-only distributions and counts.
- **`dependencies: "all"`** — a shorthand that makes **every** argument in **every** set mutually
  dependent, so you don't hard-code the dependency graph. Almost every cohort builder wants this
  (hence the shorthand); the clinic sets it on `protocol_cohort.json`. It is a relatively new
  convenience.
- **`disables`** — the inverse: "if I'm selected, **disable** these other arguments/sets." A client
  instruction, always case-specific — there is **no `disables: "all"`** shorthand.

**Value format (both `dependencies` and `disables`).** Either a **path string** to the target
argument_set, or an **array of argument/argument_set names** — not just the `"all"` keyword:

Both forms work for **both** attributes — the example below uses a path for one and a name array
for the other only to show each; either could use either:

```jsonc
// on an argument_set: this set's arguments depend on one other set, and disable two others
{ "argument_set_definition": { "argument_set_type": "optional", "name": "cohort_labs", "title": "Labs" },
  "dependencies": "protocols/argument_sets/argument_set_cohort.json",   // path form
  "disables": [ "cohort_clinic", "cohort_demographics" ],               // name-array form
  "argument_expanders": [ "protocols/data_functions/collection_set_labs.json" ] }
```

Set them **on the argument_set** (as above) for narrower scope than `dependencies: "all"` on the
protocol — e.g. only some sections interdependent. They are argument-level attributes; on the set
they apply to all the arguments the expanders generate.

## Anatomy of a (hand-crafted) argument

When you do declare one explicitly, an argument has up to three parts:

```jsonc
{
  "argument_definition": {          // the control the user sees
    "argument_type": "categorical-checkbox-filter",
    "name": "background_department",
    "title": "Department",
    "entity_name": "encounters"
  },
  "handlers": [                     // how the selection becomes a data function
    { "handler": "background_department_target",
      "handler_function": "protocols/data_functions/categorical_collection_department.json" }
  ],
  "argument_protocol": "protocols/argument_protocols/argument_protocol_department.json"  // populates options
}
```

- **`argument_definition`** — the control: its `argument_type`, `name` (how the script references
  it), `title`, and type-specific fields (`minimum`/`maximum`, `entity_name`, `suggested_value`, …).
- **`handlers`** — a `handler` name + a **`handler_function`** (a data_function). The handler turns
  the user's selection into a data function; `argument-reference` pulls *that* into the script.
- **`argument_protocol`** — a small helper protocol (usually `method: "summary"`) that **populates
  the control's selectable values** by querying the collection. Filter controls (`-filter` types)
  use it so their option list reflects the data (and can narrow as other filters are set).

Autogenerated arguments (`argument_expanders`) build these three parts for you from the data_function.

### The hand-crafted case: a boolean toggle

A `boolean` argument is the clearest thing an expander can't generate — there's no collection of
values to expand, just an on/off (or tri-state) choice. The toy ships one: the download protocol's
**"Include all DNA variants"** toggle (`argument_set_download_options.json`), whose handler is a
**`boolean` data_function** that resolves to a data function when the toggle is on:

```jsonc
{ "argument_set_definition": { "argument_set_type": "optional", "name": "download_options",
                               "title": "Download Options", "asset": "dna-mutate-line-mixed.png" },
  "argument_expanders": {
    "argument_type": "boolean-null",           // tri-state: on / off (null)
    "name": "include_all_dna_variants",
    "handlers": { "handler": "include_all_dna_variants",
      "handler_function": {
        "data_function_type": "boolean",
        "true_function": { "data_function_type": "bundle", "criteria": [ /* the genotype collections */ ] } } } } }
```

Three things worth internalizing (each cost a real debugging cycle):
- **`boolean-null` means the OFF state is `null`** — it contributes nothing — so you name only the
  **`true_function`** and no `false_function` is needed. (Plain `boolean` sends a real `false`, which
  *does* invoke a `false_function`; prefer `boolean-null` for a simple on/off toggle.)
- **Consume it with `argument-reference`** (to the argument), **not `argument-set-reference`** (to the
  set) — a single boolean's handler output is an argument reference; pointing an argument-set-reference
  at it throws "no matching argument_set." The download's `analysis_variables` lists
  `{ "data_function_type": "argument-reference", "argument": "include_all_dna_variants" }`.
- **A boolean composes** — `boolean` wraps a `bundle` wraps data_functions (`composition.md`).

## Common argument types

| argument_type | Control | Use it for |
|---|---|---|
| `cohort` | the interactive cohort builder | a user-assembled entity subset (`cohort-builder.md`) |
| `categorical-checkbox` | multi-select checkboxes of a collection's levels | pick several values of one categorical collection |
| `categorical-checkbox-filter` | same, but the option list **narrows** as other filters are set | the workhorse cohort filter |
| `categorical-radio` / `categorical-radio-filter` | single-select of a collection's levels | choose exactly one value |
| `categorical-paste` | paste a list of values/IDs | bulk selection (e.g. a list of subject IDs) |
| `numeric-range` | a min/max slider on a numeric variable | filter by a range (Systolic 130–160) |
| `timestamp-range` | a date range | filter by a date window (endemic in clinical data) |
| `boolean` / `boolean-null` | a toggle (`-null` adds a tri-state "unset") | an on/off option |
| `static-categorical` / `static-radio` | a **fixed** option set not drawn from the data | an algorithm choice, a display mode |
| `static-numeric` | a fixed numeric range/value | a threshold not tied to a collection |
| `categorical-input` | a free-text box | an arbitrary string input |

The **`-filter` variants** are the ones you want inside a cohort builder: they use their
`argument_protocol` to show only values present in the current (narrowed) data, and `static-*`
types are for choices that don't come from the data model at all.

## How the script consumes an argument

Three bridges (full semantics in `catalog-data-function-types.md`):

- **`argument-reference`** → the data function the argument's **handler** produced (the normal path
  for filters).
- **`argument-set-reference`** → the combined handlers of a whole argument_set (how a cohort
  builder ANDs its filter sections).
- **`argument-value`** → the argument's **raw value** as sent from the client, in place of a data
  function — for plain strings, and for a **cohort `background`** (whose value already *is* a data
  function). This is why a cohort background uses `argument-value`, not `argument-reference`.

## Recipe: add an argument to a protocol

1. Prefer **`argument_expanders`**: list the data_function(s) for the collections you want as
   controls in an argument_set — done.
2. If you must hand-craft: write the `argument_definition` (type + `name` + `title`), a `handler`
   with a `handler_function` (the data_function), and an `argument_protocol` if it's a `-filter`
   type that needs populated options.
3. Put the argument_set in the protocol's `protocol_definition.argument_sets`.
4. Reference the selection from the `script` with the right bridge (`argument-reference` for a
   handler's output; `argument-value` for a raw value or a cohort background).
5. `compile` — the engine validates every reference resolves; satisfy any `mandatory` argument in
   the protocol's test.

## Common mistakes

- **Hand-crafting arguments** an `argument_expander` over a data_function would generate.
- **`argument-reference` on an argument with no handler** — the compiler warns; use `argument-value`
  if you want the raw value.
- **A `-filter` control with no `argument_protocol`** — its option list won't populate.
- **Referencing an argument by the wrong `name`** — the name in the script must match the
  `argument_definition.name` exactly.
- **Forgetting a `mandatory` argument in the test** — the protocol errors at test time.

Rarer types (and the exact type-specific attributes) vary — **confirm against a working FC** before
copying. Next: `cohort-builder.md` — the key protocol every FC needs, built from these arguments.
